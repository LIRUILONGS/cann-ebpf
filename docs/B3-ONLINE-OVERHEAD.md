# B3：V4 在线固定负载开销 smoke（2026-11-26）

状态：**服务不停机的在线 smoke 完成**；正式 ≤3% 门禁仍建议在隔离/受控负载下复测。

## 1. 方法

- V4 保持运行，不重启、不注入；
- `scripts/overhead_fixed_load.py`：2 并发、固定 2 条短 prompt、`max_tokens=32`、每轮 30 秒；
- 每轮同时 `attach --blocking off/on`，窗口取 `capture_start`→`capture_stop`；
- 客户端统计成功请求/延迟，vLLM `/metrics` 统计服务端计数，agent 读 `/proc`。

## 2. 结果

| 指标 | off | on | 变化 |
|---|---:|---:|---:|
| 客户端成功请求 | 30 | 32 | +6.7% |
| 客户端 req/s | 0.999 | 1.066 | **+6.7%（无下降）** |
| 客户端 p50 | 2.497s | 2.507s | +0.4% |
| 客户端 p95 | 4.737s | 3.096s | -34.6% |
| agent CPU | 1.27% | 1.33% | +0.06pp 单核 |
| agent RSS 峰值 | 45.5MB | 41.3MB | 噪声范围 |
| dropped span | 0 | 0 | — |
| `/health` | 200 | 200 | 正常 |
| service | active | active | 正常 |

客户端口径门禁：吞吐没有下降、p95 没有回归，**通过在线 smoke**。

## 3. 为什么不用 vLLM 总计数下结论

同窗口 vLLM 总计数为：off `26 req / 58,778 tokens`，on `23 req / 34,829 tokens`，
按服务端计数算会得到 -11.6% 的“下降”。但这是**同机生产流量与批处理/caching 波动**：
客户端固定负载实际完成数反而略高，e2e/ttft 分布也差异很大。因此：
- **门禁使用客户端固定负载指标**；
- 服务端 `/metrics` 只作为参考，在线共用流量下不能作为 A/B 判据。

## 4. 结论与建议

- 在线 smoke：agent 单核 CPU +0.06pp、RSS 无实质变化、0 丢事件、服务正常；
- 这不能替代正式 ≤3% 门禁：正式门禁需要隔离实例或严格低峰、固定并发/输入/输出长度、多轮中位数；
- 建议在维护窗口跑 `--repeats 3` 的隔离版本，或使用备用实例。
